 A) QUÉ ES Y CÓMO FUNCIONA
===============================================================================

QUÉ ES
------
Antes: ~7 programas de escritorio en Python/Tkinter (uno por PC), compilados a
.exe, cada uno con sus credenciales pegadas en el código.

Ahora: UNA sola aplicación web (framework Reflex) que corre en el servidor de la
oficina. Los usuarios entran con el navegador a http://192.168.2.181:3000, con
usuario y contraseña. Cuando se actualiza el código, todos ven la versión nueva
al recargar (F5) — no hay que reinstalar nada en ningún PC.

Módulos migrados (cada uno = una sección del menú lateral):
  - Empleados (gestión / CRUD / carga masiva / historial)
  - Roles de pago (PDF individual y por lote)
  - Reportes de nómina (consolidado + histórico + comparador)
  - Préstamos (historial combinado + saldos + análisis IA)
  - Observaciones / multas / faltas
  - Registrar egresos/ingresos (BIESS + manual + masivo)
  - Liquidaciones / finiquitos (4 pantallas: Generar / Editor / Gestión / Descuentos)
  - Vacaciones (gozadas / pagadas / cálculo / comprobantes PDF+QR / dashboard)
  - Bitácora / agenda de cobro
  - Administración (usuarios, roles, auditoría, parámetros)


ARQUITECTURA (2 capas + 3 bases de datos)
-----------------------------------------

   Navegador  ─▶  Reflex (insevig_web/)  ─▶  core/  ─▶  Bases de datos
                  (interfaz web)             (lógica     ├─ SQL Server 2008 R2
                                              de negocio)│   (192.168.2.115, "insevig")
                                                         │   — FUENTE DE VERDAD, filtro
                                                         │   CODEMP='10' AND CODSUC='10'.
                                                         │   Lectura casi siempre; escritura
                                                         │   mínima (RPEMPLEA/RPEMPOBSERV/RPINGDES).
                                                         ├─ Supabase (nube, PostgREST)
                                                         │   — espejo de las tablas de SQL Server
                                                         │   + tablas propias de módulos
                                                         │   (vac_*, liquidaciones*, descuentos_*,
                                                         │   bitacora*…). Toda escritura acá deja
                                                         │   auditoría.
                                                         └─ PostgreSQL local (en el server)
                                                             — SOLO datos de la app:
                                                             usuarios/roles, audit_log, jobs,
                                                             historial de préstamos migrado del
                                                             SQLite viejo, configuración.

  * core/  = Python puro, SIN interfaz. Se puede testear solo (pytest). Único
    lugar con credenciales (core/config.py lee de un archivo .env).
  * insevig_web/  = la web (Reflex). NO tiene lógica de negocio: llama a core/.
  * Cada módulo es una "rebanada" independiente:
        core/repos/<mod>.py         (consultas + operaciones del módulo)
        core/excel/<mod>_*.py       (Excel del módulo)
        core/pdf/… (si aplica)
        insevig_web/states/<mod>_state.py   (estado + eventos de la pantalla)
        insevig_web/pages/<mod>/*.py        (las pantallas)
        docs/modulos/<mod>.md              (contrato + estado)
    Un módulo no importa a otro módulo; la coordinación entre módulos vive en
    la capa de estado de la web.

  * "Jobs": las operaciones largas (Excel de 2.5M filas, envío de correos,
    análisis IA) corren en segundo plano y la pantalla muestra una barra de
    progreso. El backend es UN solo proceso (no hace falta más para ~10
    usuarios).

  * Selector de fuente: casi toda pantalla de consulta deja elegir SQL Server o
    Supabase. Si SQL Server no responde (sin driver, sin red), cae a Supabase.
    Las ESCRITURAS van siempre a SQL Server (lo mínimo) o a Supabase con
    auditoría, según el módulo.

DÓNDE VIVE
----------

  \\192.168.2.181\Sistemas_Dev$   = E:\Sistemas_Dev\   (unidad X:)  → el CÓDIGO.

        El .exe lanzador (solo abre el navegador). RRHH tiene lectura/ejecución.

La app corre como SERVICIO de Windows llamado  insevig-web  (con NSSM):
  - arranque automático al prender el servidor
  - se reinicia solo si se cae
  - comando real:  .venv\Scripts\reflex.exe run --env prod --single-port --frontend-port 3000
  - logs en  C:\insevig\logs\insevig-web.{out,err}.log

Componentes en el servidor:
  - Python 3.12 + entorno virtual  E:\Sistemas_Dev\...\.venv
  - PostgreSQL 16  (BD "insevig_app": usuarios, auditoría, jobs, préstamos migrados)
  - archivo  .env  con TODAS las credenciales (ACL restringida)
  - (pausado) Caddy como proxy HTTPS — hoy la app se sirve directo en :3000, solo
    en red local + Tailscale (100.98.34.99:3000)


QUÉ HACE UN DESPLIEGUE / ACTUALIZACIÓN  (deploy/windows/deploy-nas.ps1)
---------------------------------------------------------------------
Correr en el NAS, como Administrador, dentro de E:\Sistemas_Dev\NOMINA_ROLES_SISTEMA_INSEVIG:

    .\deploy\windows\deploy-nas.ps1 -SoloActualizar

Pasos que ejecuta:
  1. git pull --ff-only                       (baja el código nuevo de GitHub)
  2. .venv\Scripts\pip install -e ".[web]"    (instala/actualiza dependencias)
  3. valida el .env y su ACL
  4. python -m scripts.healthcheck            (¿SQL Server + Supabase + Postgres OK?)
  5. alembic upgrade head                     (aplica migraciones de BD si hay)
  6. python -m insevig_web.seed               (asegura el usuario admin)
  7. (solo en instalación) regla de firewall TCP 3000 + registra el servicio NSSM
  8. Restart-Service insevig-web
  9. prueba http://localhost:3000/  → si responde 200, listo.

El frontend (React) lo compila Reflex al arrancar el servicio. La primera vez o
tras un cambio grande de estilos tarda ~45 s (a veces se borra la carpeta .web
para forzar recompilación desde cero).

Actualización "en caliente" mínima (lo que se hace en el día a día):
    git pull  →  pip install -e ".[web]"  →  Restart-Service insevig-web
El usuario solo tiene que apretar F5.


¿SE PUEDE HACER CON ALGÚN PROGRAMA / AUTOMÁTICO?   → SÍ. Opciones:
-----------------------------------------------------------------

1) UN SOLO CLIC (lo más simple).
   Un acceso directo / .bat en el escritorio del NAS que ejecuta:
       powershell -ExecutionPolicy Bypass -File `
         E:\Sistemas_Dev\NOMINA_ROLES_SISTEMA_INSEVIG\deploy\windows\deploy-nas.ps1 -SoloActualizar
   El operador hace doble clic y espera ~1 min. Es lo que hoy se corre a mano.
   (Se puede empaquetar como .exe con "Bat To Exe Converter" o "IExpress" si se
   quiere un ícono propio, pero el .bat ya alcanza.)

2) AUTOMÁTICO AL HACER git push  (recomendado para no depender de nadie).
   Instalar en el NAS un "self-hosted runner" de GitHub Actions (un servicio
   más). Un workflow del repo, al hacer push a main, dispara en el NAS:
       git pull → pip install → alembic upgrade → Restart-Service insevig-web
       → curl http://localhost:3000 para confirmar.
   Resultado: subís el código y a los ~1-2 min ya está en producción, sin tocar
   el servidor. Requiere: el runner instalado + el servicio con permiso para
   `Restart-Service insevig-web`.

3) TAREA PROGRAMADA (Task Scheduler de Windows).
   Una tarea que cada noche (o cada X horas) corre `deploy-nas.ps1 -SoloActualizar`.
   Sencillo, pero despliega "a ciegas" — si un commit rompe algo, entra igual.
   Sirve como complemento del punto 1 (si alguien olvidó desplegar).

4) WEBHOOK.
   Un mini servicio que escucha un POST de GitHub ("push a main") y lanza el
   script. Igual que el punto 2 pero más artesanal; el runner de Actions es más
   robusto.

5) BOTÓN DENTRO DE LA PROPIA APP  (solo para admin).
   Una página /admin que, al pulsar "Actualizar sistema", ejecuta el script en
   el servidor y muestra el log. Cómodo, pero da a la app permiso para
   reiniciarse y correr pip — hay que sopesar el riesgo. Preferible el punto 2.

RECOMENDACIÓN: punto 1 ya, y punto 2 (runner de GitHub Actions) cuando se quiera
que el despliegue sea "push y listo" sin entrar al NAS.
